Lesson 6 · 17 min

Closing the loop: failure log and observability

What isn't observed isn't cultivated. This lesson follows a clinic front-desk agent from its first error to supervised autonomy, and shows the minimum you need to record to replace "I think it got better" with "it improved from 88% to 95%".

Start the lesson

In this lesson you will

  1. 1How an error becomes a permanent rule
  2. 2Comparing agent versions with numbers
  3. 3Minimum observability: three fields
  4. 4Finding the error pattern worth fixing first

Goal: record each run with the minimum set of fields and turn a real error into a new rule, comparing the result before and after.

  1. 1/7

    Starting environment

    Doctors and specialties, each doctor's hours, procedures and duration, clinic rules, and access to the schedule. The agent only suggests; the receptionist approves each appointment.

  2. 2/7

    First failure

    The agent books 7:30 PM with a doctor who doesn't see patients after 6 PM. The schedule showed "free," but a free schedule slot is not an available doctor. The failure is logged with date, decision, result, and root cause.

  3. 3/7

    New rule

    "Before suggesting, check the schedule AND the doctor's working hours. Outside working hours, never, even if the schedule shows free." Takes effect from the next run onward.

  4. 4/7

    Evaluation

    Of the next 20 interactions, 18 were correct. The 2 failures become two more rules: the procedure's duration must fit in the time slot, and 15 minutes between appointments.

  5. 5/7

    Stabilization

    40 interactions in two weeks: 20/20 in each, zero corrections from the receptionist, response time from 4 minutes to 45 seconds.

  6. 6/7

    Autonomy

    With the history, the agent starts confirming on its own. The human gets a daily report and reviews only what the agent flagged as an exception: cutoff time, new patient, long procedure.

  7. 7/7

    After 2 months

    Rules: from 5 generic ones to 14 born from real failures. 320 runs logged, 7 failures documented, 97.8% accuracy, version v1.0 → v1.4. The model is the same as on day one; if the clinic switches models, the garden stays.

02 · The difference between two versions

What observability shows (project example, 100 runs in each version).

1. v1.0 · 88%

Three error patterns: outside the professional's hours (5), time slot too short for the procedure (4), and an ambiguous reply about cancellation (3).

Each pattern produced a new rule: four rules modified.

2. v1.1 · 95%

Patterns 1 and 2 disappeared. Pattern 3 dropped from 3 to 1 occurrence.

A new pattern showed up: two simultaneous procedures requesting the same exam room. The cycle goes on.

The investmentFrom 88% to 95% with rules and fixes. Nobody switched the model: they looked at the data and adjusted the environment.

3. What you can decide

Compare versions on the same scenarios. Find patterns ("70% of errors are long procedures"). Measure the cost of an error ("each rescheduling costs R$ 150"). Decide where to invest first.

04 · Practice

One week of observation.

1 · One week of logging

5 min a day

For the function you chose, log every run in EXECUCOES.md with the three minimum fields.

Done when: the file has at least 10 rows and you can state the week's accuracy rate (e.g., 8 out of 10).

2 · A rule born from an error

20 min

Take the failure that repeated most during the week and fill in the "from failure to rule" template. Put the rule in the file and bump the version.

Done when: the rule is written in the agent's file, the version went up (v1.0 → v1.1), and the next runs are being counted so you can compare.
